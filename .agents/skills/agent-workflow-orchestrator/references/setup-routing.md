# Runtime Confirmation and Routing

`config.example.json` is a **shared workspace template only**; it does not choose the implementing agent. Store independent model candidates at `.agent-workflow/routing/claude-code.json` and `.agent-workflow/routing/codex.json` (plus optional `.agent-workflow/routing/other.json` for user-configured external models), selected by the **verified invoking agent identity**, not the last agent that initialized the repo. Preserve `.agent-workflow/config.json` for shared execution settings and legacy compatibility; a historical Claude-led value there must not control Codex. Obtain explicit user confirmation of real available tools, per-provider quotas, permissions, reviewer availability and delegation depth. No script in this package launches providers or validates credentials.

Default safely to one orchestrator and sequential subtasks. **Nested opt-in:** `delegate-tree` can propose depth 2 (Root→Sub-Orchestrator→Worker) but the distributed session must confirm actual nested spawning permission, worker ownership/isolation, cost and global limits. The candidate config may declare `delegation.max_depth:2` and a higher `max_parallel_workers` only after an authorized setup; for parallel values above 1, structural validation additionally requires `setup.status:"confirmed"`, `delegation.runtime_capabilities` with `supportsConcurrentWorkers`, `enforcesOwnership`, and `enforcesIsolation` all true, plus `task_execution.mode:"bounded_parallel"` and a global `max_active_child_tasks` not below the requested count. **These are user-supplied capability claims, not runtime proof or permission to launch.** The nested CLI always stays PLAN_ONLY. A runtime-specific dispatcher needs separate verification, authorization, and actual global cap enforcement. A worker must pass an actual bounded interaction before treating it as ready. Routing fallback arrays describe possible eligible candidates; **never** switch providers automatically or because quota is low. Ask for user instruction and verify original task owner stopped.

Verify required external Skill readiness **per executing worker**, especially `karpathy-guidelines` for code changes, using `DEPENDENCIES.md`. A confirmed model mapping is not proof of Skill loadability. The optional pre-plan `grill-with-docs` interview requires explicit activation and its two upstream sub-skills.

## Optional model/effort profiles

For an interactive user-invoked interview rather than manually choosing or editing JSON, load the separate canonical Skill `.agents/skills/configure-models/SKILL.md`. In Claude Code install its `.claude/skills/configure-models/SKILL.md` adapter for `/configure-models`; in Codex invoke `$configure-models`. It asks only for missing runtime/model/effort decisions, previews changes and requires **separate explicit approval before writing** the invoking agent's own `.agent-workflow/routing/<agent>.json`. Use read-only `orasqill models preview`, `orasqill models resolve claude-code|codex|other --workspace .` and `orasqill models validate` helpers. Loading a Skill does not itself authorize provider activation, model switching or config writes.

Orasqill includes two **preconfigured advisory presets**, plus an unconfigured third **Other Model** preset in `.agent-workflow/profiles/`: `other-orchestrator.json` (empty role choices, user supplies provider/runtime/model), alongside `openai-orchestrator.json` (Codex/GPT coordinates, Claude reviews) and `claude-orchestrator.json` (Claude coordinates, Codex/GPT reviews). Both use the same version-1 local config shape and remain `setup.status: unconfirmed`. The selected profile is a **role suggestion**, not a runtime dispatcher.

Select routing **by verified invoking agent**, using `orasqill models resolve claude-code|codex|other --workspace .` (the `other` target must be explicitly requested by the user): prefer the corresponding agent-local config, then a matching historical shared config, then an unconfirmed built-in matching preset. Never adopt the opposite agent's historical profile. The `--profile claude-led|openai-led` bootstrap options initialize only the **matching agent-local candidate**; `--profile other` initializes only the optional custom third route. Plain `oranit` initializes the existing Claude Code and Codex defaults, **not** the Other route. Shared config is neutral on new workspaces, not a global leader selector. The `routing.*.preferred` array identifies candidates for orchestrator, implementer and separate reviewer. `stage_preferences` includes `triage`, `plan`, `implement`, `scoped_implement`, `complex_implement`, `computer_use`, `review`, `critical_review` and `final_report` recommendations. A stage containing only `role` inherits that role's preferred candidate; a stage with `runtime/model/effort` explicitly overrides the candidate for **that stage alone**. Never interpret a recommendation as an instruction to launch an agent or override an authorized worker.

Before execution, verify each proposed `runtime`, exact model ID, supported effort setting, real available credentials/tools, and external Skill loadability **in the actual agent session**. These sample IDs represent provider API names; Claude Code/Codex UI model selection and effort controls may differ from API names. Record confirmed values and permissions in the correct agent-local config only after trusted user setup; keep shared limits separate and never activate workers as a side effect. Other Model candidates may use any nonempty user-verified `runtime` adapter ID and `model` identifier, with an optional `provider` label. If that external adapter does not expose compatible effort levels, omit `effort`. This is an **advisory mapping only** and provides neither adapter installation nor permission to call an external API. If unsupported, report `SETUP_REQUIRED` rather than silently substitute a model; the `fallback` lists are empty and `automatic_switching` is false.

**Terra specialist decision:** `scoped_implement` uses `gpt-6.1-terra` / `high` in OpenAI-led for small deterministic fixes with focused regression tests; in Claude-led it inherits the main Claude Sonnet Implementer at `medium`. `computer_use` proposes Terra / `medium` for screen/UI actions in both profiles. This remains advice only: Terra must be available in the actual Codex runtime, API tool calls use the Responses API, and any Claude→Codex handoff requires the user's authority and independent worker readiness. Do not replace Sol/Astra for complex coding or downgrade independent reviewers. Uncertain, cross-service, or HIGH_RISK implementation should remain with a separately approved higher-capability role. This mapping introduces **no automatic routing or switching**.

**Claude-led reviewer detail:** `review` resolves to GPT-6.1 Sol with `xhigh` reasoning. `critical_review` resolves to GPT-6.1 Sol with `effort: "max"` plus `requested_mode: "ultra"` (the user's requested Ultra mode). On OpenAI's API the valid `reasoning.effort` values for GPT-6.1 Sol include `xhigh` and `max`, **not `ultra`**. Ultra is a separate multi-agent option on eligible Codex clients. The profile does **not** claim to enable it, override the sequential worker limit, or convert Max into Ultra. An authorized user must explicitly confirm runtime support and selection; otherwise return `SETUP_REQUIRED`, not a silent substitution. Distinct reviewers must still be independent of the change's author.

The implementer must load the original `karpathy-guidelines` Skill before writing code. A reviewer needs **separate eligible ownership**, actual diff evidence and independence from the author; a different model string alone does not prove independence. HIGH_RISK still requires an independent review and specific authorization for protected actions. The stage-specific `critical_review` effort is a recommendation, never a way around these gates.

High-risk tasks need separate independent review and any extra protected-action approval. Do not use a child reviewer who is the sole author as an independent reviewer. The scheduler is advisory only: it cannot prove isolation, budget or authorization. Treat missing confirmation as `SETUP_REQUIRED`.
