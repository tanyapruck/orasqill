# Runtime Confirmation and Routing

`config.example.json` is a **template only**; its unconfirmed state cannot authorize a worker. Copy to `.agent-workflow/config.json` in a consuming repo, configure candidate runtimes/models, then obtain explicit user confirmation of real available tools, per-provider quotas, permissions, reviewer availability and delegation depth. No script in this package launches providers or validates credentials.

Default safely to one orchestrator and sequential subtasks. A worker must pass an actual bounded interaction before treating it as ready. Routing fallback arrays describe possible eligible candidates; **never** switch providers automatically or because quota is low. Ask for user instruction and verify original task owner stopped.

Verify required external Skill readiness **per executing worker**, especially `karpathy-guidelines` for code changes, using `DEPENDENCIES.md`. A confirmed model mapping is not proof of Skill loadability. The optional pre-plan `grill-with-docs` interview requires explicit activation and its two upstream sub-skills.

## Optional model/effort profiles

Orasqill includes two **advisory presets** in `.agent-workflow/profiles/`: `openai-orchestrator.json` (Codex/GPT coordinates, Claude reviews) and `claude-orchestrator.json` (Claude coordinates, Codex/GPT reviews). Both use the same version-1 local config shape and remain `setup.status: unconfirmed`. The selected profile is a **role suggestion**, not a runtime dispatcher.

Select a profile **only by the user's instruction**; copy its entire content to `.agent-workflow/config.json` in the consuming repository after checking existing local configuration. The `routing.*.preferred` array identifies candidates for orchestrator, implementer and separate reviewer. `stage_preferences` adds `triage`, `plan`, `implement`, `complex_implement`, `review`, `critical_review` and `final_report` recommendations. A stage containing only `role` inherits that role's preferred candidate; a stage with `runtime/model/effort` explicitly overrides the candidate for **that stage alone**. Never interpret a recommendation as an instruction to launch an agent or override an authorized worker.

Before execution, verify each proposed `runtime`, exact model ID, supported effort setting, real available credentials/tools, and external Skill loadability **in the actual agent session**. These sample IDs represent provider API names; Claude Code/Codex UI model selection and effort controls may differ from API names. Record confirmed values and permissions in local config only after trusted user setup. If unsupported, report `SETUP_REQUIRED` rather than silently substitute a model; the `fallback` lists are empty and `automatic_switching` is false.

**Claude-led reviewer detail:** `review` resolves to GPT-6.1 Sol with `xhigh` reasoning. `critical_review` resolves to GPT-6.1 Sol with `effort: "max"` plus `requested_mode: "ultra"` (the user's requested Ultra mode). On OpenAI's API the valid `reasoning.effort` values for GPT-6.1 Sol include `xhigh` and `max`, **not `ultra`**. Ultra is a separate multi-agent option on eligible Codex clients. The profile does **not** claim to enable it, override the sequential worker limit, or convert Max into Ultra. An authorized user must explicitly confirm runtime support and selection; otherwise return `SETUP_REQUIRED`, not a silent substitution. Distinct reviewers must still be independent of the change's author.

The implementer must load the original `karpathy-guidelines` Skill before writing code. A reviewer needs **separate eligible ownership**, actual diff evidence and independence from the author; a different model string alone does not prove independence. HIGH_RISK still requires an independent review and specific authorization for protected actions. The stage-specific `critical_review` effort is a recommendation, never a way around these gates.

High-risk tasks need separate independent review and any extra protected-action approval. Do not use a child reviewer who is the sole author as an independent reviewer. The scheduler is advisory only: it cannot prove isolation, budget or authorization. Treat missing confirmation as `SETUP_REQUIRED`.
